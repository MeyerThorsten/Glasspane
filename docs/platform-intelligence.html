Architecture

Two rules every feature follows.

  • Pure logic, injected data. Scoring, graph construction, and rule evaluation are pure functions receiving domain records as input. Only lib/services/* touches the (currently mock) data sources — when real APIs arrive, the intelligence layer does not change.
  • Existing conventions, zero new dependencies. Client components use useCustomer() with service calls in useEffect; widgets register in config/widget-registry.ts and appear via config/view-configs.ts; pages get their own layout wrapper.

1 · Vertical Intelligence

Problem

Glasspane claims to serve every industry, but a hospital and a logistics carrier saw identical dashboards with identical targets. Nothing in the product knew the customer's vertical.

Solution

A registry of vertical profiles (config/vertical-registry.ts) and a benchmark engine (lib/verticals/benchmark.ts) grading actuals against industry targets.

Manufacturing TISAX · ISO 27001 · NIS2
Healthcare HIPAA · GDPR · ISO 27799
Financial Services DORA · PCI DSS · ISO 27001
Retail PCI DSS · GDPR
Public Sector BSI Grundschutz · NIS2 · GDPR
Energy & Utilities KRITIS · NIS2 · IEC 62443
Technology SOC 2 · ISO 27001
Logistics NIS2 · ISO 28000
General (fallback) ISO 27001 · GDPR

resolveVerticalProfile(industry) resolves exact match → partial/alias match → General. No customer is ever unprofiled.

2 · Ontology Explorer

Problem

Each dataset lived in its own widget. There was no way to ask the Palantir question: "this thing broke — what does it touch?"

Solution

A typed entity graph per customer plus a drill-down Explorer page at /explorer: search, entity detail, direct relations, and blast-radius analysis.

EntityRelationNotes
customer(root)industry, tier
servicecustomer —subscribes→ servicestatus, uptime, SLA target
incidentincident —affects→ serviceseverity, MTTR
changechange —targets→ servicerisk, schedule
costCategorycustomer —spend-on→ costCategoryspend, budget
certificatecertificate —secures→ customerissuer, expiry
cvecve —threatens→ serviceseverity, affected system

Dangling references are never dropped: an incident pointing at a decommissioned service links to the customer node instead, keeping the inventory complete.

Pure query layer (lib/ontology/queries.ts): getNeighbors (direction + relation kind), blastRadius (breadth-first, hop-tagged), findEntities (search across label, kind, status, metadata), graphSummary.

3 · Computed Zero Outage

Problem

The Zero Outage Score — the product's headline metric — was a hardcoded JSON value. The marketing said "measured"; the code said "constant".

Solution

lib/zero-outage/compute.ts derives all three pillars from live operational signals, with graceful fallback to the static data when signals are missing.

PillarSignals (stretch target)
PeopleEngagement avg (90 pts) · Opportunity readiness avg (85 pts)
ProcessesChange success rate (98 %) · P1 MTTR score (95 pts) · Patch compliance (98 %)
PlatformsSLA attainment via error-budget burn (100 pts) · Security score (95 pts) · Backup success (99.9 %)
  • Metric attainment = min(100, value / target × 100) — over-performance can't mask gaps.
  • Pillar score = mean attainment, graded against the conventional 95-point target.
  • MTTR curve: ≤ 60 min on P1 → 100 pts; ≥ 480 min → 0; linear between.
  • SLA attainment: each multiple of the error budget burned beyond target costs 25 points — five-nines targets degrade gradually instead of collapsing on the first miss.
  • Fallback: an entirely signal-less pillar voids the computation and the service returns the static JSON.

Consumers: the dashboard banner, the C-Level Zero Outage Score widget, and the Business Zero Outage Pillars widget — all consistent now.

4 · Action Center

Problem

Every widget described state; none prescribed a response. The "so-what" was left to the reader.

Solution

A deterministic rules engine (lib/actions/rules.ts) converts the operational snapshot into ranked recommended actions with rationale and concrete steps — the top widget on the C-Level view.

Vertical-aware thresholds mean a hospital is held to stricter patch and change standards than a retailer. Each action's relatedEntity id matches an ontology node id — the two features share one identity scheme.

Testing

33 unit tests in tests/platform/ on the Node test runner (same harness as tests/ai/).

npm run test:platform   # verticals, ontology, zero outage, action rules
npm run test:ai         # existing AI suite
npm test                # both suites

Additionally verified with npm run typecheck, npm run lint, npm run build, and a Playwright smoke pass over /explorer and the C-Level dashboard.
